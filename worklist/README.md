# worklist (POC)

One store for everything that needs doing.

**Decide where it lives before you commit it.** If the host repo's remote is not yours (a client
or employer org), gitignore `worklist/` and give it its own nested git repo with a private
remote. If the host repo is yours, committing it is fine.

## Architecture

```
worklist/
  items/w001-slug.md        one file per item — the only source of truth
  attachments/w001/         captured email bodies etc, kept OUT of the item file
  views/                    100% generated, never hand-edited
    index.md  index.html    complete list, one short line per item
    today.md                the `now` band + overdue + stale chases
    waiting.md              what other people owe you
  bin/render.mjs            deterministic renderer, no LLM, no dependencies
  config.json               band caps + overflow policy — the only tunable file
  inbox.md                  raw captures, one line, zero decisions
```

**The governing principle: judgment at write time, determinism at read time.**
An agent decides once, when filing, and writes it into frontmatter. Every view is
regenerated by a plain script. An LLM never writes a view. That is the trust architecture:
if a view is ever wrong you re-render it, you do not argue with a model.

## Item contract

| Field | Values | Notes |
|---|---|---|
| `id` | `wNNN` | identity; never changes, never reused |
| `title` | one line | must fit an index row |
| `status` | `now` `side` `next` `waiting` `later` `done` | cascading WIP caps, set in `config.json` (default **now 1, side 3, next 7**) |
| `hat` | closed list (see below) | what mode the work is in; the day is batched by this |
| `impact` | 1-3 | 3 requires a falsifiable consequence in the body |
| `effort` | S M L | |
| `due` | date or empty | |
| `due_source` | `external` `committed` `self` `none` | who the date belongs to; stops self-invented urgency |
| `owner` | name or empty | **empty by default** — assigning yourself is a decision |
| `waiting_on` | person or empty | who has the ball; a `waiting` item with a name here goes under "Chase these" after 3 days |
| `until` | date or empty | parks the item until that date, then it comes back on its own; the "remind me in September" gate |
| `labels` | free tags | filtering only, never ordering |
| `visibility` | `private` `team` | pre-wires the future team view |
| `started` | date or empty | you have begun it — never move it out of `now` without asking |
| `parent` | `wNNN` or empty | one level only — no epics of epics |
| `blocked_by` | `wNNN` ids, space/comma separated | gates the item until every blocker closes |
| `artifacts` | `kind:key \| label \| url` | `jira:` `slack:` `email:` `pr:` `claude:` `session:` `web:` `file:` |

`waiting_on` used to take a date as well. The renderer still reads a date there as `until`, so
older items render as before. Write new dates to `until`, and move an old one across the next
time you edit its item.

**Deliberately absent:** priority, story points, sprint, workflow status. Their absence is
what stops this becoming a second Jira. Rank is computed, never stored.

Body sections: `## Why this matters`, `## Next action`, `## Reply draft` (optional),
`## Log`, `## Captured`. Sources render last in the detail view, under everything else.

## Capture

**One line is one item** — any number of links plus any free-text thought on the same line.
Next line is the next item. Blank lines ignored. No other syntax.

Two modes, differing only in latency:

| | How | What happens |
|---|---|---|
| **stash** | say "stash this" + lines, in session; or the browser hotkey; or a Slack reaction | appended raw to `inbox.md`. No fetching, no decisions. |
| **file now** | paste the lines and ask me to file them | fetched, followed and written into `items/` immediately |

`process the inbox` drains stashed lines through the same filing path.

### Filing follows links transitively

Filing is not "record that a link exists". For each captured line: fetch it, read the whole
thread, and **follow every link it contains** — a Slack thread linking another Slack thread,
a PR, a ticket, a doc — recursively, gathering what each contributes. The item must stand
alone. Opening it should never require going somewhere else to understand it.

Every fetched location is listed under **Sources** at the bottom of the detail view, so the
provenance is there without being in the way.

Where the next action is a reply, filing also writes a `## Reply draft` into the item. It is
text in the item file, **not** a draft created in Slack or Gmail. The point is that going
back to Slack costs a paste, not a re-read.

### Sub-tasks: checklist or separate item?

**Default to a checklist in the body.** Promote a step to its own item only when it needs its
own status, owner or date, or when someone else could pick it up. The practical test is the
same one used for merging: *would this be worked in the same sitting?* If yes, it is a
checkbox, not an item.

This matters because splitting eagerly destroys the point of the caps. Forty items where
twenty are fragments of five projects makes `next` unreadable.

A genuinely big topic gets **one item** holding the accumulated context and the checklist. If
part of it becomes independently schedulable, spin that out with `parent: wNNN`. One level
only — a parent's detail view lists its children, and each child links back.

### Dependencies

`blocked_by: wNNN` gates an item exactly the way `until` does: it drops out of the live bands
and comes back on its own when the blocker closes. Two triggers, one mechanism.

**Stated blockers gate. Inferred blockers do not.** If you say B waits on A, gate it. If
*you* infer it from a thread, record it and show it, but leave the item pickable — a wrong
dependency hides work silently, which is the same failure as a wrong merge.

### Grouping

Your grouping is binding: links you put on one line are one item, always. Connections I spot
that you did not make are surfaced as *possible duplicate of wNNN*, never merged silently.

## config.json

The one tunable file. Both `bin/render.mjs` and the skill read it, so a change here changes
both what the renderer reports and how the agent bands. Delete it and the defaults below apply.

```json
{
  "caps": { "now": 1, "side": 3, "next": 7 },
  "overflow": "enforce-interactive",
  "tracks": []
}
```

| Key | Values | Meaning |
|---|---|---|
| `caps` | whole numbers, 1 or more | how many items each live band holds |
| `overflow` | `tolerated` `enforce-interactive` `enforce-autonomous` | what happens when a band is at cap and something new belongs in it |
| `tracks` | array of label strings | labels for work with reserved time elsewhere; see Tracks below |

**`overflow` is the decision worth thinking about.** The bands are meant to be full, so almost
every new item arrives at a band with no room:

- **`tolerated`** — put it in, let the band run over. The count still shows, without a warning.
- **`enforce-interactive`** — something must leave. If one candidate is clearly weakest the agent
  displaces it and tells you in one line; if the call is close it asks you.
- **`enforce-autonomous`** — same, but it never asks. It decides and reports.

Either `enforce-` mode means a band never ends a turn over cap. An item you have marked
`started` is protected only in `now`, where it is never displaced silently in any mode; in `side`
and `next` it weighs against displacement but does not block it. A bad value stops the render with
a message naming the key, rather than falling back to a cap you did not choose.

## Tracks

A **track** is work whose time is reserved outside the list, in the calendar: a standing block
for something that is not the main job. Put its label in `tracks` in `config.json`. Empty by
default, because most weeks do not work that way.

Track items always sit in `later`. They do not compete for `now`/`side`/`next` and are never
backfill candidates, because they are not competing for the same hours — the block already
holds them. The merit ranker would bury them regardless: track work is self-dated, never
overdue, and never unblocks anyone else. Pick the top track item at the start of a block;
whatever you do not finish becomes a new track item in `later`.

`TRACKS` in `render.mjs` lists which labels get a filter chip. That chip is the block-start view:
open it, take the top item, and file whatever is unfinished at the end of the block as a new
`later` item with the same label.

### Filtering is one radio set

Bands, hats and tracks are **one** selection, never a combination. You are looking at a band, or
at a hat, or at a track. Clicking any chip replaces the current view; clicking the active chip
returns to `now`. Combining them was worse than useless: a hat left selected silently narrowed
every subsequent view, and there is no reading of "side ∩ a track label" worth a click.

A hat or a track spans bands, so those views open every band that has a hit and show the
**filtered** count in the band header. Only the unfiltered `all` view keeps the
collapsed-by-default shape and the `x/CAP` counts.

## Claude Code session artifacts

```
session:<session-id-or-name> | <friendly name> — <what it was> | [working directory]
```

**The URL slot is not a URL here.** `render.mjs` generates the real link, because it has to: for
each `session:` artifact it writes a Warp **Tab Config** to
`~/.warp/tab_configs/worklist-<id>-<key>.toml` and rewrites the URL to `warp://tab_config/<stem>`.
Clicking the source in the HTML view opens a new Warp tab and runs
`cd "<dir>" && claude --resume "<key>"`.

**The third field is an optional working directory, and it is load-bearing.** Claude Code stores
sessions **per project directory** (`~/.claude/projects/<cwd-slug>/`), so resuming from the wrong
cwd silently finds nothing — and a fresh Warp tab can inherit whatever directory you were last in.
Leave it empty and the tab lands in this repo, which is right for sessions run from here. Set an absolute
or `~/` path for a session started somewhere else (another project's repo, a client clone):

```
session:9f3c… | auth-refactor — token rotation spike | ~/code/other-project
```

Both `directory` and an explicit `cd` are written, so the cwd is correct even if Warp restores a
different one.

Why a Tab Config and not `warp://action/new_tab?path=…`: new_tab cannot carry a command
([Warp #5859](https://github.com/warpdotdev/Warp/issues/5859)). Tab Configs have a `commands`
array that runs on open. Verified against Warp 0.2026.07.08.

**Prefer the session id over the name.** An id resumes straight into the conversation; a name only
opens the `--resume` picker filtered to that search term. To resolve a name to its id:

```bash
grep -l "Session renamed to: <name>" ~/.claude/projects/<project-slug>/*.jsonl
```

Keep the human-readable name in the **label** — that is what renders in Sources and becomes the
Warp tab title.

## Email artifacts

```
email:<RFC822-Message-ID> | <subject> — <one-line summary> | <deep link>
```

The Message-ID is the canonical key: stable, client-independent, and it survives changing
mail client. Render the subject plus a one-line summary of what the mail is about and what
it wants from you, and link **out** to the client.

**Body capture is opt-in, not the default.** Capture the body into `attachments/` only when
the item is read-only reference material. If the next action is "reply", you have to open
the client anyway, so an inlined body is dead weight that also bloats the item file.

**Deep links are yours to wire up.** The worklist links out to whatever tools you already use,
and it has no integrations of its own: no mail client, no tracker, no chat. If you want an
`email:` artifact to open in your mail client, find that client's URL scheme and use it in the
deep-link slot. Same for anything else — a tracker, a docs tool, a dashboard. Two fallbacks work
everywhere: a web permalink, and the `message:<Message-ID>` scheme for mail.

The same applies to fetching. The agent resolves a link with whatever tools it has connected, so
if you want it to read your mail, your tracker or your chat, connecting those (MCP servers, CLIs,
whatever your setup uses) is a step you do yourself. Nothing here does it for you.

## Fixtures

`bin/make-fixtures.mjs` generates fabricated items carrying `fixture: true`, marked `fx` in
the index and badged in the HTML. `--clean` deletes every fixture and leaves real items
untouched.
